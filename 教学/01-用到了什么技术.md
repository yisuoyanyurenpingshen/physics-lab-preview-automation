# 01 · 用到了什么技术

这套东西不复杂，但横跨了几层。下面按「目标系统是什么 → 我用了什么 → 关键技术点」的顺序拆开讲。

---

## 一、目标系统的技术栈（逆向出来的）

先要知道对面是什么，才能选对打法。

| 层 | 是什么 | 怎么判断出来的 |
|---|---|---|
| 前端框架 | **Vue 3 + Element Plus** | 页面上所有交互组件都带 `el-` 前缀的 class（`el-radio`、`el-checkbox`、`el-button`）；DOM 是客户端渲染出来的，查看源代码几乎为空 |
| 构建工具 | **Vite** | 静态资源路径形如 `/assets/index-29f210d5.js` —— 文件名带内容哈希，是 Vite 的默认产物命名 |
| 公式渲染 | **MathJax** | 题目里的公式不是图片也不是纯文本，而是被渲染成 Unicode 数学字符（`𝑉`、`𝑑`、`Δ`、`φ`），这是 MathJax 的特征 |
| 后端框架 | **Django REST Framework** | 列表接口返回 `{count, next, previous, results}` 四件套，这是 DRF 分页器的固定格式 |
| 认证方式 | **JWT（SimpleJWT）** | 登录返回 `{access, refresh}` 两个 token；token 是 `xxx.yyy.zzz` 三段式，解 base64 能看到 `token_type` / `exp` / `user_id` / `role` |
| 路由 | 单页应用 | 地址栏变但页面不刷新；`/login`、`/student/previews`、`/student/answer/{id}` 都是前端路由 |

> **这一节的通用套路**：拿到一个陌生网站，先按 F12 看三个地方——Network（接口长什么样）、
> Sources（前端代码打包在哪）、Application（登录态存在哪）。这三处看完，系统的骨架就清楚了。

## 二、我这边用到的技术

整体是**两层结构**，这是这套方案最重要的设计决定：

```
┌─────────────────────────────────────────────┐
│  Bash 编排层  (lib.sh / run_all.sh)          │  ← 负责流程、判断、跳过逻辑
├─────────────────────────────────────────────┤
│  API 层  (api.js)                            │  ← 走 HTTP 接口，快、稳、可判断
│    登录 / 续期 / 读任务 / 读题目 / 读得分      │
├─────────────────────────────────────────────┤
│  浏览器层  (agent-browser + clickgen.js)      │  ← 走真实页面，做"提交"这个动作
│    注入登录态 / 勾选选项 / 点提交按钮          │
└─────────────────────────────────────────────┘
```

**为什么要分两层？** 因为两件事的最优解不同：

- 「读状态、判断该不该做」——用 HTTP 接口最快最准，不用等页面渲染，也不怕页面改版。
- 「提交答卷」——用真实浏览器点真实按钮，行为和人在用浏览器时完全一致，最不容易出问题。

如果全用浏览器做，慢且脆；如果全用接口做，就得自己拼请求体，反而更容易出错、也更难说清「和人工操作等价」。

### 具体技术清单

| 技术 | 用在哪 | 备注 |
|---|---|---|
| **REST API / HTTP** | `api.js` 全部接口调用 | 用到 GET / POST / PATCH，`Authorization: Bearer` 头 |
| **JWT 与令牌续期** | 登录、401 自动重试 | access 约 30 分钟过期，refresh 约 7 天 |
| **浏览器自动化（CDP）** | `agent-browser` | 通过 Chrome DevTools Protocol 驱动真实浏览器 |
| **DOM 查询与事件触发** | `clickgen.js` | `querySelectorAll` + `element.click()` |
| **正则表达式** | 文本归一化、页面取数 | 匹配"已作答 N / M""本次得分 xx 分" |
| **Unicode / 码点处理** | 公式题匹配 | 数学字母、希腊字母的映射 |
| **Node.js** | `api.js` / `clickgen.js` | 用内置 `fetch`，无第三方依赖 |
| **Bash** | 流程编排 | 循环、条件跳过、函数库 |
| **Git / GitHub REST API** | 代码托管 | 沙箱里 git 推不出去时改用 API 推送 |

**零第三方依赖**（Node 侧）：只用 Node 18+ 自带的 `fetch`，不需要 `npm install` 装任何包。
这是刻意的取舍——给别人用的工具，依赖越少越不容易装不上。

## 三、关键技术点（这些是真正的难点）

### 难点 1：选项顺序是随机的

**现象**：同一套题，刷新两次，选项顺序不一样；题目顺序也会变。
接口返回里有个 `option_orders` 字段，每次请求的值都不同。

**后果**：任何「点第 1 个选项」「答案是 B」的写法都会随机出错。

**解法**：**按选项的文本内容匹配**，完全无视顺序。

```js
// 不要这样 —— 顺序会变
card.querySelectorAll(".el-radio")[1].click();

// 要这样 —— 按文本找
labels.forEach(el => {
  if (norm(el.innerText) === norm("氩原子的第一激发电位")) el.click();
});
```

> **可迁移的经验**：凡是"题"类系统，只要选项顺序会随机，答案就必须存**内容**而不是**位置**。

### 难点 2：公式被渲染成了奇怪的字符

**现象**：题目里的 $V_H = R_H \frac{I_S B}{d}$ 在页面上取 `innerText`，拿到的是
`𝑉𝐻=𝑅𝐻𝐼𝑆𝐵𝑑` —— 一堆看起来像字母但和 ASCII 字母**不是同一个字符**的东西。

**原因**：MathJax 用 Unicode 的「数学字母数字符号」区段（U+1D400–U+1D7FF）来排版，
`𝑉` 是 U+1D449，不是 ASCII 的 `V`（U+0056）。字符串直接比较必然不相等。

**解法**：写一个归一化函数，把所有花体变体映射回 ASCII，再比较。

```js
// 数学斜体大写 A-Z 在 U+1D434 开始，逐个映射回 'A'-'Z'
s.replace(/[\u{1D400}-\u{1D7FF}]/gu, c => {
  const cp = c.codePointAt(0);
  const ranges = [[0x1D434, 0x1D44D, 65], /* ... */];
  for (const [lo, hi, base] of ranges) {
    if (cp >= lo && cp <= hi) return String.fromCharCode(base + cp - lo);
  }
  return c;
});
```

希腊字母也一样（`Δ` `φ` `λ`），而且**有好几套变体**：普通希腊字母、数学斜体、数学粗斜体……
归一化函数把拉丁字母、希腊字母（含斜体变体）统一映射，再删掉 `·`、`×` 这类排版符号和所有空白。

> **可迁移的经验**：处理富文本/公式/排版内容时，**先归一化再比较**。
> 这也解释了为什么两段"看起来一样"的文字在程序里不相等。

### 难点 3：多选题只记录到最后一个

**现象**：一道多选题有 3 个正确选项，用循环连着 `click()` 三次，结果只有最后一个被选中。

**原因**：Element Plus 的复选框是受控组件，点击会触发 Vue 的响应式更新 + 重新渲染。
同步连点的时候，后面的点击可能作用在**还没更新完的旧状态**上，最后互相覆盖。

**解法**：逐个点击，每次之间留出渲染时间。

```js
for (const box of targets) {
  box.querySelector("input").click();
  await new Promise(r => setTimeout(r, 150));   // 等它更新完
}
```

> **可迁移的经验**：操作现代前端框架渲染的界面时，"点一下等一下"往往不是笨办法，
> 而是必要的。这也是**同步代码 vs 异步渲染**这个概念的典型体现。

### 难点 4：不同题目的选项文本一模一样

**现象**：某一套里有两道题，选项都是「反射光栅 / 透射光栅」，但正确答案一个选前者、一个选后者。
全局按文本匹配会同时选中两道题，必然错一道。

**解法**：答案库里支持"按题干关键字限定范围"——先找到题干包含某个关键字的题卡，
只在**这张卡片内部**匹配。

```jsonc
"multiQ": {
  "根据对入射光的调制作用": ["振幅光栅", "位相光栅"],
  "根据衍射光的方向":     ["反射光栅", "透射光栅"]
}
```

> **可迁移的经验**：数据有重复时，必须引入**作用域**（scope）。
> 这和编程里"避免全局变量"是同一个道理。

### 难点 5：怎么保证不重复提交

系统给每套题 **3 次作答机会**，用完了就没了。所以自动化脚本最大的风险不是"做不对"，
而是"把机会浪费光"。

**解法**：提交前先查一次作答记录，做三道闸：

```
已满分（100 分）        → 跳过
已用次数 ≥ 3            → 跳过（没机会了）
配置为"不重做"且已作答   → 跳过
只有三个条件都不满足，才真的去做
```

这个设计有个正式名字叫 **幂等性（idempotency）**：反复运行同一个脚本，结果一致，
不会因为多跑了一遍就产生额外副作用。写自动化脚本、定时任务、数据同步时都是核心要求。

### 难点 6：Windows 上的路径陷阱

**现象**：Git Bash 里 `pwd` 得到 `/c/Users/future/xxx`，把这个路径传给 Windows 版的
`node.exe`，报错 `Cannot find module 'C:\c\Users\future\xxx'`。

**原因**：`/c/` 是 Git Bash（MSYS2）模拟出来的挂载点，Windows 原生程序不认识，
于是把它当成「当前盘下的 `c\Users\...`」。

**解法**：用 `cygpath -m` 转成两边都认的 `C:/Users/...` 形式，或者让脚本用 `__dirname` 自己算路径。

> **可迁移的经验**：跨平台脚本里，**不要假设路径格式通用**。这是 Windows 上做开发最常踩的坑之一。

### 难点 7：沙箱里 git 推不出去

**现象**：`git push` 报 `schannel: server closed abruptly`；换 OpenSSL 后端、显式配代理，
全部在 TLS 握手阶段失败。但同一台机器上，Node 访问 `https://api.github.com` 完全正常。

**解法**：既然 API 通，就**用 REST API 完成推送**——先上传文件内容（blob）、再建目录树（tree）、
再建提交（commit）、最后更新分支引用（ref）。产出的是一个正常的 commit，不是"伪提交"。

这里还踩到一个坑：**空仓库不能先调 blob 接口**（返回 409 `Git Repository is empty`），
必须先用 Contents API 写一个文件把分支建出来。

> **可迁移的经验**：一条路走不通时，先判断是**链路问题**还是**能力问题**。
> 这里是链路被拦，能力（GitHub 的读写接口）其实一直都在。

## 四、技术选型的取舍

| 选择 | 备选方案 | 为什么这么选 |
|---|---|---|
| 用 agent-browser | Selenium / Puppeteer / Playwright | 环境里已有；且它支持"打开真实浏览器 + 跨命令保持会话"，调试时能直接看到页面 |
| 用 Node 内置 fetch | axios / requests | 零依赖，别人拿到就能跑 |
| 用 Bash 编排 | Python / Node 单文件 | 编排逻辑就是循环和判断，Bash 最短；也方便老师直接看懂改哪一行 |
| 答案库用 JSON | 数据库 / Excel | 纯文本、可 diff、随手可改、不需要任何工具就能编辑 |
| 提交走浏览器点击 | 直接调提交接口 | 与人工操作完全一致，行为最透明 |

---

## 五、一句话总结

这套东西的技术含量不在"难"，而在**把一件跨层的事拆干净**：

> 用 HTTP 层解决"读和判断"，用浏览器层解决"做"，用 Bash 层解决"顺序和边界"，
> 用归一化解决"看起来一样但程序认为不一样"，用幂等性解决"反复跑会不会出事"。

每一条都是可迁移的工程习惯，换个场景照样用得上。
