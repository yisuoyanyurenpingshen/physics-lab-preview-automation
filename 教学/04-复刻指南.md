# 04 · 给你的课程做一套

如果你想给**自己课程**的某个在线系统做一套类似的工具，这份文档是路线图。
顺序很重要，跳步会返工。

---

## 第 0 步（不可跳过）：先确认授权

在写第一行代码之前，先回答三个问题：

1. **这个系统是谁的？** 学校/学院/自己单位。**有没有书面或口头的授权做自动化？**
2. **你要用它做什么？** 如果是"教师批量核验题库"，通常没问题；
   如果是"替学生完成学习任务"，先停下来想清楚。
3. **会不会碰到别人的数据？** 如果会，需要额外的授权和合规评估。

> 这步花 10 分钟，能省掉后面所有的麻烦。
> 参考：[`03-这是攻击吗.md`](03-这是攻击吗.md) 第八节的六问清单。

---

## 第 1 步：摸清流程（先当一次普通用户）

**不要一上来就写代码。** 先用浏览器手动完整走一遍流程，边走边记录：

### 1.1 列出流程步骤

以本课程为例，流程是：

```
登录 → 看任务列表 → 逐套进入 → 读题 → 作答 → 提交 → 看分数
```

把它写成 checklist。**每一步都要能在浏览器里手动完成**——这是后面判断"是否越界"的基线。

### 1.2 打开 DevTools，看接口

按 F12 → **Network** 面板 → 勾选 `Fetch/XHR` → 然后手动操作一遍。

你会看到每个动作对应的请求：

| 你的动作 | 看到的请求 |
|---|---|
| 点登录 | `POST /api/auth/login/` |
| 进任务列表 | `GET /api/previews/` |
| 进某套题 | `GET /api/previews/1/questions/` |
| 点提交 | `POST .../submit/` 或页面自身逻辑 |
| 看记录 | `GET /api/attempts/` |

**重点看三样**：请求方法、请求路径、返回的 JSON 结构。
把返回结构复制下来（右键 → Copy response），后面建模要用。

### 1.3 看登录态存在哪

F12 → **Application** 面板：

- **Cookies** 里有 → 存在 cookie
- **Local Storage** 里有 → 存在 localStorage
- **Session Storage** 里有 → 存在 sessionStorage
- 都没有 → 可能存在内存里（每刷新就重新登录）

这一条决定了后续怎么让脚本"保持登录"。

### 1.4 找特殊规则

手动走一遍的时候，注意记录**系统给的各种限制**：

- 每套题能做几次？
- 有没有时间限制、截止时间？
- 提交后能不能看到标准答案？
- 有没有必须人工确认的弹窗？

**这些限制是后面必须遵守的，不是要绕过的。**

---

## 第 2 步：设计数据层（答案库）

数据层就是"把正确答案存在哪、怎么存"。这是整套东西里**最需要动脑**的部分。

### 2.1 先搞清题目类型

从第 1 步拿到的 JSON 里看，题型通常有这么几种：

| 题型 | 特征 | 存法 |
|---|---|---|
| 单选 | 选项里只能选一个 | 存**选项文本** |
| 多选 | 可以选多个 | 存**该题所有正确选项的文本数组** |
| 判断 | 只有"正确/错误"两个选项 | 存**题干关键字 → 正确/错误** |
| 填空 | 有输入框 | 存**题干关键字 → 答案字符串** |

### 2.2 三条铁律

**铁律 1：存文本，不存位置。**

```jsonc
// ❌ 错：系统打乱顺序后必然答错
"singles": { "第3题": 2 }

// ✅ 对：不管顺序怎么变都能命中
"singles": ["氩原子的第一激发电位"]
```

判断依据：**看接口返回里有没有 `order` / `option_orders` / `shuffle` 之类的字段**，有就说明顺序会变。

**铁律 2：用题干关键字做作用域。**

如果发现不同题目的选项文本会重复，就必须支持"按题干限定"：

```jsonc
"multiQ": {
  "根据对入射光的调制作用": ["振幅光栅", "位相光栅"],
  "根据衍射光的方向":     ["反射光栅", "透射光栅"]
}
```

**铁律 3：库要能增量修正，不要推倒重来。**

用纯文本 JSON（而不是二进制/数据库），这样：
- 随手能改，不用工具
- 能用 git 记录每次改动
- 出问题时能对比前后差异

### 2.3 答案怎么来（这是最需要想清楚的一步）

三种来源，各有适用场景：

| 来源 | 适用 | 注意事项 |
|---|---|---|
| **依据学科知识作答** | 通用，最正当 | 需要你对这门课真的懂 |
| **参考系统自己给出的标准答案** | 系统对本人开放时才可用 | 用完要把"参考了系统标准答案"如实记录，并确认是否符合课程评分规则 |
| **请出题老师提供** | 教师自用 | 最干净的路径，建议优先 |

## 第 3 步：做执行层

### 3.1 决定用浏览器还是直接调接口

| 方案 | 优点 | 缺点 | 建议用于 |
|---|---|---|---|
| **浏览器自动化** | 行为和人工完全一致，最透明 | 慢，怕页面改版 | **提交、需要交互的动作** |
| **直接调 HTTP 接口** | 快、稳、好判断 | 需要自己拼请求体 | **读取状态、判断该不该做** |

**推荐两层都用**（本项目就是这么做的）：接口层负责"看和判断"，浏览器层负责"做"。

### 3.2 浏览器自动化的关键写法

```js
// 1) 按文本找元素，而不是按下标
const labels = [...document.querySelectorAll(".el-radio__label")];
labels.forEach(el => {
  if (norm(el.innerText) === norm("正确答案文本")) el.click();
});

// 2) 多选要逐个点，中间留出渲染时间
for (const box of targets) {
  box.querySelector("input").click();
  await new Promise(r => setTimeout(r, 150));
}
```

**归一化函数是必需品**，不是可选项。任何带公式、上下标、特殊符号的题目都需要它：

```js
function norm(s) {
  s = String(s).replace(/^[A-Z]\s*\.\s*/, "");        // 去掉 "A." 前缀
  s = unicodeMathToAscii(s);                          // 𝑉 → V
  s = greekToAscii(s);                                // Δ → D，φ → phi
  s = s.replace(/[\u00B7\u22C5\u00D7]/g, "");         // 去掉 · ×
  s = s.replace(/\s+/g, "");                          // 去掉所有空白
  return s;
}
```

### 3.3 常见坑（提前避开）

| 坑 | 症状 | 对策 |
|---|---|---|
| 选项随机排序 | 同一套两次分数不同 | 按文本匹配 |
| 富文本/公式 | 看起来一样但比较不相等 | 归一化后再比 |
| 组件库状态合并 | 多选只记住最后一个 | 逐个点 + 延时 |
| 选项文本重复 | 串题 | 按题干限定作用域 |
| 判断题和单选题同结构 | 误匹配 | 判断题按题干关键字单独处理 |
| 登录态不在 cookie | 读 cookie 拿不到 | 看 Application 面板，注入到正确的地方 |

## 第 4 步：做编排层（防重复提交）

**这一步决定工具是"能用"还是"敢用"。**

任何会消耗有限资源的自动化（作答次数、接口配额、提交名额），都必须先查状态再动手：

```
for each 任务:
    查当前状态
    if 已完成:            → 跳过
    if 剩余次数 <= 0:     → 跳过
    if 配置为不重做且已做:  → 跳过
    否则:                 → 执行
```

这套逻辑叫**幂等**：同一个脚本跑 1 遍和跑 10 遍，最终结果一样，不会产生额外副作用。

**必须做到的三件事：**

1. **跑之前先打印完整状态**——让人一眼看到"现在什么情况"。
2. **跑之后再打印一次状态**——让人核对"到底做了什么"。
3. **每一个跳过都要说明原因**——"已满分，跳过"而不是默默跳过。

---

## 第 5 步：让它能被别人用

脚本自己能跑 ≠ 别人能跑。差的就是这几样：

| 要做的事 | 具体做法 |
|---|---|
| **配置外置** | 地址、账号、任务列表全放 `config.sh`，代码里不写死 |
| **给配置模板** | `config.example.sh`，别人复制改名就能用 |
| **保护敏感配置** | `.gitignore` 忽略真实配置文件，防止误传 |
| **零依赖或极少依赖** | 优先用运行时自带的库 |
| **不硬编码路径** | 用 `__dirname` / 脚本自身位置定位，别写绝对路径 |
| **写中文说明** | 别人不会读你的代码，只会读你的文档 |
| **给一个"只看不动"的命令** | 例如 `node scripts/api.js previews`，让人先看状态再决定 |

---

## 第 6 步：验收

做完拿这几条对一遍：

- [ ] 手动操作一遍流程，确认脚本行为**和人工一致**
- [ ] 跑一次"看状态"的命令，确认输出清晰可读
- [ ] **连续跑两次完整的脚本**，确认第二次全部跳过、没有重复提交
- [ ] 故意填错一个答案，确认脚本能指出"哪道题没答上"
- [ ] 换一台机器（或换个目录），确认不需要改代码就能跑
- [ ] 检查仓库里**没有**账号密码、令牌、学生个人信息
- [ ] 读一遍 [`03-这是攻击吗.md`](03-这是攻击吗.md) 的六问清单

---

## 第 7 步：想清楚"要不要给出去"

这是最后一步，也是最容易被忽略的一步。

工具一旦交出去，**它的用途就不再由你控制了**。同一个脚本：

- 在教师手里 → 批量核验题库、生成参考答案
- 在学生手里 → 跳过预习过程

**如果你的目的是"减少重复的机械劳动"，那它没问题；
如果你发现它正在被用来跳过学习本身，那应该在文档里明确写清不建议的用法。**

这一点本项目是这么处理的：工具包里的 `教师使用说明.md` 和教学文件夹里的
`03-这是攻击吗.md` 都明确写了"不建议用它代替学生完成预习"。

---

## 附：通用套路总结

不管换成什么系统，这七步都是同一套：

```
0. 确认授权         ── 不跳
1. 手动走一遍       ── 用 DevTools 摸清接口、登录态、限制
2. 建数据层         ── 存内容不存位置，支持作用域，纯文本可增量
3. 做执行层         ── 接口读 + 浏览器做，富文本先归一化，多选逐个点
4. 做编排层         ── 先查状态，幂等，跳过要有理由
5. 让别人能用       ── 配置外置、零依赖、不硬编码路径、写中文说明
6. 验收             ── 尤其是"连跑两次不出事"
7. 想清楚用途       ── 别让工具变成替学生跳过学习的东西
```

**其中第 0 步和第 7 步是判断题，其余是技术题。**
技术题做错了可以改，判断题做错了，工具越好用反而越麻烦。
